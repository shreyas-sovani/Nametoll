# x402 plugin

Sign x402 payment challenges using hiero-cli managed keys. The payer private key
never leaves the KMS — the command builds and signs a transfer but does **not**
submit it; the x402 facilitator adds its fee-payer signature and submits.

## End-to-end flow (agent-driven)

The CLI does **not** make HTTP requests. The agent runs them:

1. **GET** the target URL.
2. If status `402`, read the `PAYMENT-REQUIRED` response header (header names are
   case-insensitive). Decode/inspect its payload — confirm `accepts[]` contains a
   `scheme: "exact"` entry whose `network` is `hedera:mainnet` or `hedera:testnet`.
   If not Hedera, this CLI cannot help.
3. Pass the **raw header value** to the CLI:
   `hcli x402 sign --challenge "<PAYMENT-REQUIRED value>"`
   (add `--asset` if the challenge offers several; `--from` for a non-operator payer).
4. Take `paymentSignatureHeader` from the output.
5. **Retry the same request** with header `PAYMENT-SIGNATURE: <paymentSignatureHeader>`.
6. The facilitator validates + submits; the retry returns the real `200` data.

```bash
# the agent runs these HTTP calls, not the CLI
HDR=$(curl -sD - -o /dev/null https://api.example.com/data | grep -i '^payment-required:' | cut -d' ' -f2-)
SIG=$(hcli x402 sign --challenge "$HDR" --output json | jq -r .paymentSignatureHeader)
curl -s -H "PAYMENT-SIGNATURE: $SIG" https://api.example.com/data
```

Requires a configured network and operator (or `--from` payer) — see the
prerequisites in `SKILL.md`. The payer must be funded; balance/association are
checked by the facilitator at settlement.

---

### `hcli x402 sign`

Decode a `PAYMENT-REQUIRED` header, build a partially-signed Hedera
`TransferTransaction` (debit payer / credit `payTo`; HBAR `0.0.0` or an HTS
token), KMS-sign it, and return the `PAYMENT-SIGNATURE` header value.

| Option          | Short | Type   | Required | Default        | Description                                                                                              |
| --------------- | ----- | ------ | -------- | -------------- | -------------------------------------------------------------------------------------------------------- |
| `--challenge`   | `-c`  | string | **yes**  | —              | Value of the `PAYMENT-REQUIRED` header from the 402 response                                             |
| `--from`        | `-f`  | string | no       | operator       | Payer: `accountId:privateKey`, key reference `kr_xxx`, or account alias. Defaults to network operator    |
| `--asset`       | `-a`  | string | no       | —              | Asset to pay with when the challenge offers several. `0.0.0` = HBAR, or an HTS token id. Required only on multi-asset challenges |
| `--key-manager` | `-k`  | string | no       | config default | Key manager: `local` or `local_encrypted`                                                                |

**Example:**

```
hcli x402 sign --challenge "<PAYMENT-REQUIRED value>" --from 0.0.5005
hcli x402 sign --challenge "<PAYMENT-REQUIRED value>" --asset 0.0.0
hcli x402 sign --challenge "<PAYMENT-REQUIRED value>" --asset 0.0.456858 --output json
```

**Output:** `{ paymentSignatureHeader, payer, payTo, amount, asset, network, feePayer, transactionId }`

The agent drives the HTTP flow itself (GET → `402` → retry): it reads the
`PAYMENT-REQUIRED` header off the 402 response, passes it as `--challenge`, then
sets the returned `paymentSignatureHeader` as the `PAYMENT-SIGNATURE` header on
the retry. The CLI does not make HTTP requests.

**Notes:**

- Supports `hedera:mainnet` and `hedera:testnet` only; other networks are rejected.
- No client-side preflight: payer balance and token association are validated by
  the facilitator at settlement, after this command returns.
